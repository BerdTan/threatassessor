# Anti-Slop Web

## The protocol — do all of it, in this order

Do not skip a step because the page looks small or the brief looks obvious. Skipping is how the output ends up generic, and every step below exists because omitting it produced slop.

0. **Route.** Page already exists? → `references/retrofit.md`, follow that instead. Blank file? → continue.
1. **Ask the user about direction.** Before writing any code. See Phase 0 — this is mandatory unless the brief already pins the style down.
2. **Write the premise block** (Phase 1). Show it to the user with the code.
3. **Derive the tokens** from four decisions (Phase 2). Emit them as code before any markup.
4. **Read `references/banned-defaults.md`** before writing markup. Not after.
5. **Build** under the four structural rules (Phase 3).
6. **Run `check.py`, fix everything, re-run** (Phase 4).
7. **Run `shoot.py`, open the PNGs, and look at them.** Answer its questions in writing, *then* check yourself against `measured.json`.
8. **Have a fresh subagent review the screenshots** with no knowledge of what you intended (Phase 4, step three).
9. **Self-audit out loud** against `references/self-audit.md` — every line, with evidence.
10. **Do one full revision pass.** Mandatory. The first render is a draft.
11. **Report**: premise, what you changed in revision, what you left and why.

Throughout, `references/staying-honest.md` describes how this workflow gets faked without anyone intending to. Read it once before you start.

If you cannot do step 7 (no browser), say so plainly. An unverified build is a guess with better priors — do not describe it as checked.

## Why generic output happens

AI design output looks samey for one mechanical reason: at every decision point the model independently picks the highest-probability option. Inter. `blue-600`. `rounded-lg`. `shadow-sm`. Three-up feature grid. Identical `py-20` on every section. Each choice is individually defensible — which is exactly why it gets picked — but they were made independently, so nothing agrees with anything else.

Design personality is *correlation*. A human designer commits to one premise, and the type, spacing, color, layout, and copy all fall out of it. That shared origin is what reads as intentional. Forty uncorrelated safe choices read as a template, because statistically a template is precisely that.

So the job here is not "add creativity." It's: **reduce the number of independent decisions, ban the modal option on the ones that remain, and verify by looking.**

## Pick the path first

**Does the page already exist?** Generated by AI, inherited, or just described as looking generic?

→ **Yes: read `references/retrofit.md` now and follow it instead.** The phases below assume a blank file and will actively mislead you on existing code — you'll swap fonts and colors, the checker will go green, and the generic *layout* will survive untouched. That outcome is worse than no audit, because it certifies the result. Retrofit runs structure-first, tokens-last, and starts with a triage call.

→ **No, building from scratch:** continue below. Work through the four phases in order and don't skip to code.

## Phase 0 — Ask the user what it should feel like

**Do this before Phase 1, before any code.** Taste is the user's call, not yours. Guessing it and then defending the guess for four phases is the most expensive mistake available here, and "it looked generic" is usually what happens when nobody asked.

Ask with a real question tool if you have one (`AskUserQuestion`), otherwise ask in plain text and wait. Offer **concrete, named directions with visible consequences** — not "modern vs classic", which means nothing and gets a shrug. Pull the options from `references/house-styles.md` and describe each by what the user will actually see:

> **Direction** — pick one:
> - **Editorial / print** — big serif display, generous margins, hairline rules, no cards. Reads like a magazine feature.
> - **Industrial / utilitarian** — mono type, sharp corners, dense data, one loud signal colour. Reads like a control panel.
> - **Soft / crafted** — warm off-white paper, humanist type, hand-set feel, lots of air. Reads like a small studio.
> - **Brutal / loud** — enormous type, hard colour blocks, full-bleed slabs. Reads like a poster.

Ask at most three questions, and only ones whose answer changes what you build:

1. **Direction** (above) — always ask.
2. **Attitude in one word** — what should someone feel in the first two seconds? Confident, calm, urgent, precise, warm, severe. This becomes the ATTITUDE line.
3. **Anything off-limits** — an existing brand colour, a font they must use, a competitor's look to avoid. Only ask if the brief is silent on it.

Then **say back what you heard** in one line before building: *"Industrial, precise, must keep the existing green — so mono type, radius 0, that green as the only accent."* If they correct you, that correction is the premise.

**When to skip this:** the brief already specifies the visual direction, the user has said "just build it / you decide / surprise me", or you are mid-iteration on a page whose direction is already settled. If you skip, state the direction you chose and why, so it can be argued with. Never skip silently.

**A user constraint always outranks this skill.** If they ask for Inter, or a blue gradient, or rounded cards, build that and don't lecture. Constraints from the user are not slop.

## Phase 1 — Commit (before any code)

Write a **premise block**. It is short and it is binding — every later choice must be traceable to it.

```
SUBJECT:      what this actually is, who uses it, the page's one job
ATTITUDE:     one sentence, opinionated, arguable
DIRECTION:    house style name (or "custom" + why the house styles don't fit)
NON-NEGOTIABLES: three constraints this build will not violate
SIGNATURE:    the one element the page is remembered by
```

Two rules for the premise:

**Argue it from the subject, not from a mood board.** A payroll compliance tool and a natural wine shop should not arrive at the same attitude. If the attitude sentence would fit any other product in the brief's category, it isn't a premise yet — it's a vibe. Rewrite it.

**Commit to a direction rather than deriving one from scratch.** Read `references/house-styles.md` and pick one. Each entry ships real typefaces, a scale base and ratio, a spacing unit, a palette, and a radius/shadow policy. A fully specified system you commit to beats a mediocre one you invent mid-build. Deviate deliberately and say so; drifting is what produces mush.

If the brief already pins down a visual direction, the brief wins — including when it asks for something on the banned list. Constraints from the user are not slop.

## Phase 2 — Derive the tokens

The point is arithmetic, not taste. Four decisions should generate forty values.

**Type.** One base size, one ratio, one step count. Everything else is computed.
`base 16px, ratio 1.333, steps -1..6` → 12 / 16 / 21 / 28 / 38 / 50 / 67 / 89.
Larger ratios (1.5, 1.618) give more drama and need more discipline in the quiet areas. Set the scale as CSS custom properties and use only those values.

**Spacing.** One unit, geometric or fibonacci-ish. `8 → 8/16/24/40/64/104/168`. No arbitrary in-between values.

**Color.** Pick a background posture (light / dark / tinted) and exactly one accent. The accent may appear at most three times on a viewport. Neutrals are tinted toward the accent's hue rather than pure grey — pure `#888` is a tell.

**Weight and width.** Decide the two type weights you'll use and stick to them. Three or more weights usually means the hierarchy is being carried by weight instead of by size and space, which flattens everything.

Emit the token block as code before building the layout. If a value in the finished page isn't in the token block, it's a mistake.

## Phase 3 — Build under constraint

Read `references/banned-defaults.md` before writing markup. It's the highest-leverage part of this skill: blocking the modal option forces the second choice, and the second choice is at least a *choice*.

Four structural rules, all numeric so they're checkable:

1. **Dynamic range ≥ 5×.** Largest type on the page at least five times the smallest. Slop has a range of about 2.5× and reads flat.
2. **One breathing section.** At least one section that is ≥ 60% negative space. Uniform density is uniform boredom.
3. **Break the grid once.** Exactly one element that escapes the container — full-bleed, overlapping, offset, oversized. Once. Twice is noise.
4. **Vary section rhythm.** At least three distinct vertical padding values across sections. Identical padding everywhere is the single loudest generic tell.

On content: write the real copy, not lorem and not the marketing-voice placeholder ("Empower your workflow. Seamlessly."). Generic copy makes a good layout look generic. Let the number of features be the number of real features — if it's four, do not build a three-up grid.

**Real copy means copy that is true, not copy that sounds specific.** The push for specificity here has one serious failure mode: when you don't have the number, you invent one, and the invented version passes every check and usually looks like the best thing on the page. Never fabricate measurements, comparative claims about competitors, testimonials, counts, or credentials — not even as a "worked example" under a chart. If the SIGNATURE element you want needs data you weren't given, ask for it or build a different signature. `references/banned-defaults.md` → *Invented facts* is the full rule, and it outranks the design.

On complexity: match execution to the direction. Minimal directions fail on imprecise spacing; maximalist directions fail on thin execution. Don't pick maximalist and then build three sections.

## Phase 4 — Look at it, then fix it

**This is the phase that actually separates this skill from a list of opinions.** Everything above is a proxy for a visual judgment made blind. Close the loop.

`$SKILL` below is this skill's own directory (the one holding this file, normally `~/.claude/skills/anti-slop-web`). Substitute the real absolute path — the scripts do not live in the project you're working in, so a bare `scripts/check.py` will not resolve.

```bash
python "$SKILL/scripts/check.py" <path-to-html-or-dir>          # full audit, stdlib only
python "$SKILL/scripts/check.py" <path> --build                 # tokens only, faster, mid-build
python "$SKILL/scripts/check.py" <path> --app                   # dense app/dashboard profile
python "$SKILL/scripts/shoot.py" <url-or-file> --out .shots     # needs playwright
```

`check.py` catches the mechanical failures — banned tokens, insufficient type range, uniform padding, uniform radius, glass/gradient tells — plus generic *shapes*: template hero, N-up card grid, centered-everything, logo cloud, closing CTA band. The shape checks matter most on existing code, where token fixes alone will otherwise pass a re-skinned page. Run it first; it's fast and it has no opinions to argue with.

Two things worth knowing about how it reports:

- **`--app` relaxes the type-range and section-rhythm rules.** Dense product UI has a correct answer that a landing page doesn't: compressed range and consistent panel padding. Use it for dashboards, tables and app chrome; the script suggests it when it sees app-shaped markup. Don't reach for it to silence a marketing page.
- **"could not read a type scale" is a FAIL, not a pass.** It means the dynamic-range rule never ran — usually unparsed fluid type — so nothing was verified. Check the range by hand before moving on.

`--build` skips every structural check, so a template hero can form without any signal. Run the full audit at least once before the revision pass.

`shoot.py` renders at 390 / 768 / 1440 plus full-page, and writes `measured.json` next to the PNGs.

**Step one: open the images with the view/read tool and look at them.** Reading the code you just wrote is not seeing the page. The failures that only appear visually are: unintended near-collisions, a hero that's weaker than the section below it, an accent that reads as a mistake, type that's technically 5× but doesn't feel it, and mobile reflow that stacks into an undifferentiated column.

**Step two: read `measured.json`.** It records what actually rendered — the type sizes in use, each top-level block's height and largest type, horizontal overflow at 390px, body contrast, and missing focus styles. It exists so your visual claims are checkable. `shoot.py` prints the headline findings; the JSON has the rest.

> **If your description of the page disagrees with `measured.json`, your description is wrong.** Saying "the hero dominates" when block 3 renders larger type is not a judgment call, it's an error. Cross-check before you write the audit, not after.

Measurement settles what a number can settle. It cannot tell you whether the page is *good* — composition, awkwardness, whether the accent looks intentional, whether the premise reached the pixels. That is what looking is for, and there is no substitute.

`shoot.py` deliberately does **not** print its findings — it prints the questions and writes the answers to `measured.json`. Answer from the images first, then open the JSON and check yourself. (`--reveal` prints the machine findings; using it before writing your own defeats the point.)

**Step three: get a second pair of eyes that didn't build it.** You are the worst possible judge of whether your own page reads as generic — you know what you intended, so you see it whether or not it's there. If you can spawn a subagent, do this:

> Give it **only the screenshots and the original brief**. No code, no premise, no token block, no explanation of what you were going for. Ask: *What is this page for? What did you notice first? Does it look templated or designed — and what specifically makes you say so? What feels off?*

Then compare its answers to your ATTITUDE line. If it can't infer the premise from the pixels, the premise didn't reach the pixels — that's the swap test run by someone who can actually fail it. If no subagent is available, say so, and treat your own read as the weaker evidence it is.

**Step four: self-audit against `references/self-audit.md`.** Work the list out loud, every line, with one piece of evidence each — a measured number, something you saw in the PNG, or the reviewer's words. This is not optional and it is not a summary: a line you skip is a line you failed.

Then **one full revision pass, mandatory** — the first render is a draft. Say what you changed and why.

If playwright isn't installed: `pip install playwright && playwright install chromium`. If the environment genuinely can't render, say so plainly rather than pretending the page was verified — an unverified build is a guess with better priors.

## Failure modes of this skill

Worth knowing, because both are real:

**Weird instead of good.** Off-the-mode is not the same as fitted. If the premise is distinctive but unrelated to what the product is, you've traded generic slop for boutique slop. The fix is always Phase 1: argue the attitude from the subject.

**Rule-satisfying instead of designed.** A page can pass every numeric check and still be dead — 5× range achieved by one giant orphan number, negative space achieved by one empty div. The checks are a floor, not a target. This is why Phase 4 requires looking rather than just running the script.

## Reference files

- `references/banned-defaults.md` — the block list and what to reach for instead. Read before writing markup.
- `references/house-styles.md` — six fully specified directions with real tokens. Read during Phase 0 (to build the options you offer the user) and Phase 1.
- `references/self-audit.md` — the line-by-line grading pass, with evidence required per line. Work it during Phase 4. Supersedes the old `audit-rubric.md`.
- `references/retrofit.md` — the path for existing pages. Read *instead of* the phases above when code already exists.
- `references/staying-honest.md` — how this workflow gets faked without anyone intending to, and the steps that prevent it. Read once before starting.
- `scripts/check.py` — static token/range/shape audit. Python stdlib, no install. `--build` for tokens only, `--app` for dense app UI.
- `scripts/content.py` — content inventory and diff. Mandatory gate on any retrofit: proves no fact, price, quantity or quoted block was lost. It cannot see a fact reattached to the wrong tier — read the mapping yourself.
- `scripts/shoot.py` — multi-viewport screenshots **and `measured.json`**, the rendered facts your visual claims get checked against. Needs playwright.
