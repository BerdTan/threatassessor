# Retrofit

Use when the page already exists — generated by AI, inherited, or just described as looking generic. This path is different from the greenfield build, and taking the greenfield path on existing code is the main way this skill fails.

## The failure this exists to prevent

Given existing code, the path of least resistance is to swap tokens: Inter becomes Archivo, `blue-600` becomes the accent, delete the backdrop-blur. Ten minutes, `check.py --build` goes green, done.

But tokens are the cheap layer. The layout is the expensive layer, and the layout is what actually reads as AI-generated: template hero, three-up card grid, centered everything, identical section rhythm, closing "Ready to get started?" band. Re-skinning leaves all of that intact and hands back a page that now *passes the audit* — which is worse than not auditing, because it certifies the result.

**So: structure first, tokens last.** If you find yourself editing colors before you've changed a single layout decision, you are in the failure mode.

---

## Phase 0 — Triage (do this before reading anything else)

### 1. Look before you read

```bash
python "$SKILL/scripts/shoot.py" <file-or-url> --out .shots/before
```

Open the images. Do this **before** reading the source, so you judge the page as a visitor rather than as a maintainer. Write down the three things you notice first.

### 2. Get the structural and content inventories

```bash
python "$SKILL/scripts/check.py" <path>
python "$SKILL/scripts/content.py" <path>
```

The second prints every fact, price, quantity, list item and quoted block that must appear in the output. Read it before designing — knowing there are five Pro inclusions and three tiers is what stops you from inventing a layout that only fits four.

Full audit, structure included. Ignore token failures for now — you'll fix those in Phase 3 and they'll be trivial by comparison.

### 3. Name the subject

Before proposing anything, state what the product actually is and who uses it — from the copy, the domain, the user's description. **Do this before writing the premise**, otherwise the premise anchors on the existing design and you end up describing the slop instead of correcting it. "Clean, modern, trustworthy" is what anchoring produces. If your attitude sentence would fit any competitor, you anchored.

### 4. Call it: patch, restructure, or rebuild

| Verdict | When | What you do |
|---|---|---|
| **Patch** | Layout has real bones — asymmetry, varied rhythm, content-driven grouping. Only the tokens are default. | Phase 3 only. Rare. Don't reach for this because it's easy. |
| **Restructure** | Structure is generic but the content and information architecture are sound. Most cases. | Phases 1–3 on the existing markup. |
| **Rebuild** | Structure is generic *and* content was written to fill a template (three features because the grid wanted three). | Rewrite the markup from the greenfield path, carrying **all** the content across. |

### The content line — applies to every verdict, especially rebuild

**Rebuild means rebuilding the page, never replacing the product.** Before writing anything, inventory the original: every price, plan name, tier inclusion, metric, integration, certification, testimonial with its attribution, offer term, and capability. That inventory is fixed. It all appears in the output.

What you may change is *presentation and phrasing*: heading wording, section order, layout, which claim leads, how a group is rendered. What you may not change is *what the page says is true*. "Trusted by Industry Leaders" can become a specific heading; the three named testimonials underneath it stay. "Start Your Free Trial Today" can become "Start the 14-day trial" — banned phrasing out, the actual offer intact. `$49/mo billed annually` stays `$49/mo billed annually`.

Content that is vague is not the same as content that is false. Six features described in marketing language are still six real capabilities the user sells. Rewrite the description; keep the capability. Inventing a different, more design-friendly product is the single worst outcome available on this path — it looks like great work and it is unusable.

**This is enforced by a script, not by good intentions.** Before building, capture the inventory:

```bash
python "$SKILL/scripts/content.py" <original>            # prints what must survive
```

After building, diff it. This gate is mandatory and it is pass/fail:

```bash
python "$SKILL/scripts/content.py" <original> <rebuilt>  # exit 1 if anything was lost
```

Required items — prices, quantities, standards, list items, quoted blocks — must all survive; a loss is a bug, not an edit. Advisory items are brand and product names: not auto-failed, because rewording headings legitimately drops title-case words, but read the list and confirm each removal was deliberate.

**What the gate cannot see.** It checks that each fact still appears *somewhere in the document*. It does not check what the fact is attached to. A rebuild that moves "10 seats included" from Pro to Enterprise, or promotes "SOC 2 Type II report on request" into a flat "we are SOC 2 Type II" claim, passes with every atom intact — and misstates what the customer is buying, which is worse than dropping a line. Block coverage has the same blind spot: it matches against a bag of words from the whole page, so a deleted list item slips through whenever its words happen to appear elsewhere. Run the gate, then read the tier-by-tier mapping yourself. Green means nothing was deleted, not that the offer still says the same thing.

Never pin a new subject on a retrofit. Phase 1's "pin the subject yourself" applies only to greenfield briefs with no product at all. On existing code it is the instruction that turns a redesign into a different company's website.

**Tell the user your verdict and why, in two or three lines, before doing the work.** A rebuild changes more of their file than they may expect — say so. If they'd rather patch a page you called a rebuild, patch it and note what's left unfixed.

## Phase 1 — Premise, written against the page

Same premise block as the greenfield path, plus one extra field:

```
REJECT: what the current page is doing that the new direction refuses
```

That line is the point. It makes the premise a correction rather than a description, and it gives you something concrete to check the revision against.

---

## Phase 2 — Structure, before tokens

Work down this list. Each item is a decision the original made by default; make it deliberately instead.

1. **Hero.** If it's eyebrow + headline + subhead + two buttons, replace the shape entirely. What's the most characteristic thing in this subject's world, and can it be the hero?
2. **Section rhythm.** Assign each section a size from the spacing scale based on its actual importance. Some sections should be visibly bigger than others.
3. **Grouped content.** Count the real items. If it's four, do not keep a three-up grid. If they're not peers, don't grid them at all.
4. **Alignment.** If everything is centered, pick what earns centering — usually one thing — and left-align the rest.
5. **Cards.** Ask whether separation could be done with rules, background shifts, or nothing. Cards are the default container.
6. **One grid break.** Add exactly one element that escapes the container.
7. **Closing band.** Replace the generic CTA with the specific true ask.

Re-run `check.py` after this phase, before touching color. The structural failures should be gone while the token failures remain — that ordering is the proof you did it right.

---

## Phase 3 — Tokens

Now derive the scale, spacing, and palette as in the greenfield path, and map **every** existing arbitrary value onto them. Retrofits characteristically leave forty stray values behind because only the flagged ones got fixed. Sweep the file: any size, space, or color not in the token block is a leftover.

---

## Phase 4 — Verify against the before

```bash
python "$SKILL/scripts/content.py" <original> <rebuilt>
python "$SKILL/scripts/check.py" <rebuilt>
python "$SKILL/scripts/shoot.py" <rebuilt> --out .shots/after
```

Run `content.py` **first**. If it fails there is no point looking at the page — a beautiful page describing the wrong product is worth nothing, and the failure is not cosmetic.

Open before and after side by side. Two questions the numbers can't answer:

- **Is this a different design, or the same design in new clothes?** If the wireframes match, you patched when you should have restructured. Go back to Phase 2.
- **Does the REJECT line actually hold?** Find the thing you said the new direction refuses. If it's still there, you didn't apply the premise.

Then grade against `self-audit.md`, sections B, C and D especially, and do the mandatory revision pass.

## Reporting

Show the user: the verdict from Phase 0, what structurally changed (not what colors changed), and anything you chose to leave alone and why. Keep it to a few lines. If the honest answer is that the page needed a rebuild and they asked for a patch, say what's still generic about it.
